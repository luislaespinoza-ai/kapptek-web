Saturación de comunicaciones: cuando las aplicaciones sobrecargan al sistema de controlCommunication saturation: when applications overload the control system

Kapptek · 25 de noviembre de 2026November 25, 2026 · 7 min de lectura7 min read

El sistema de control de una planta ya no conversa solo con sus estaciones de operación. Historiadores, control avanzado, sistemas de reportes, analítica y aplicaciones de terceros le piden datos y le escriben consignas todo el día. Cada una de esas aplicaciones es un cliente más, y todas comparten los mismos canales de comunicación hacia los controladores.

Un recurso limitado y compartido

Los controladores donde está configurada la lógica de control tienen una capacidad finita para atender comunicaciones. Cada lectura y cada escritura que llega desde una aplicación cliente ocupa parte de esa capacidad, y lo hace en el mismo equipo que debe ejecutar el control del proceso.

Las escrituras pesan más que las lecturas: cada una debe ser recibida, validada y aplicada. Una aplicación que escribe muchas consignas por segundo, o que las envía todas de golpe, exige al canal mucho más que una que solo lee.

Por qué nadie lo ve venir

  • Cada cliente es razonable por separado. El problema es la suma, y nadie es dueño de la suma.
  • Las aplicaciones no se conocen entre sí. Cada proveedor configura su cliente como si fuera el único conectado.
  • La carga crece de a poco. Se agregan variables, se acortan los tiempos de actualización, se instala una aplicación nueva. Ningún cambio por sí solo parece importante.
  • Aparece en el peor momento. Durante una perturbación del proceso, todas las aplicaciones reaccionan al mismo tiempo y escriben a la vez.

Cómo se manifiesta

  1. Los datos llegan con retraso o con mala calidad a las aplicaciones.
  2. Las escrituras fallan de forma intermitente o tardan en aplicarse.
  3. Las pantallas de operación se actualizan con lentitud.
  4. En el extremo, las comunicaciones del sistema de control colapsan y hay que reiniciar servicios, con efecto directo en la operación.

Qué se necesita controlar

Proteger al sistema de control no consiste en desconectar aplicaciones, sino en administrar lo que le llega. En la práctica eso significa:

  • Limitar las escrituras por segundo, para que ningún cliente pueda exceder lo que el canal soporta.
  • Agrupar en lotes lo que se lee y lo que se escribe, en lugar de enviar cada valor por separado.
  • Escribir solo cuando el valor cambia, y no repetir la misma consigna en cada ciclo.
  • Fijar tiempos de actualización acordes al proceso, no los más rápidos que permita la aplicación.
  • Conocer la carga total, y no solo la de cada cliente.

Hacerlo aplicación por aplicación, con cada proveedor, es lento y frágil: basta un cliente mal configurado para volver al punto de partida.

El papel de OPC Nexus

OPC Nexus se interpone entre los clientes OPC de la planta y el sistema de control. Ordena las escrituras por prioridad, las agrupa en lotes y limita su ritmo para que el servidor del DCS no se sature. El sistema de control deja de atender a muchas aplicaciones con comportamientos distintos y pasa a recibir un flujo único, ordenado y predecible.

Entre lo que piden los clientes y lo que llega al sistema de control actúa un motor de gestión de escrituras que combina varios mecanismos:

  • Límite de escrituras por segundo. Cada canal hacia el sistema de control tiene un tope configurable que no se excede. La demanda que lo supera espera su turno y se escribe al ritmo permitido.
  • Lotes. Muchas escrituras viajan en una sola llamada, lo que aprovecha la capacidad del servidor con menos comunicaciones.
  • Prioridades. Las escrituras se atienden por nivel de prioridad, de modo que un comando del operador no queda esperando detrás de miles de valores informativos.
  • Banda muerta. Los cambios menores a un umbral definido por variable no se escriben, para no gastar capacidad en variaciones insignificantes.
  • Caducidad. Una consigna que quedó obsoleta mientras esperaba, por ejemplo durante una caída de comunicación, se descarta en vez de escribirse tarde.
  • Orden garantizado. Los valores de cada variable se conservan y se escriben en secuencia: una rampa llega completa. Si el servidor está caído o saturado por mucho tiempo, se conserva el valor vigente y no una historia obsoleta.
  • Cortacircuitos. Si el servidor deja de responder, OPC Nexus deja de insistir y reintenta de forma gradual, en lugar de seguir cargando a un sistema que ya está en problemas.

Cada canal se regula por separado, por lo que un problema en uno no afecta a los demás.

Ver la suma, por fin

OPC Nexus también hace visible lo que antes nadie veía. Muestra la demanda de cada sistema cliente junto a lo que efectivamente sale hacia el sistema de control, qué fracción del límite se está usando y quién consume más. La diferencia entre ambas cifras es la presión que el puente está amortiguando.

El resultado es que se pueden sumar aplicaciones a la planta sin poner en riesgo la estabilidad del sistema de control.

A plant's control system no longer talks only to its operator stations. Historians, advanced control, reporting systems, analytics and third-party applications request data and write setpoints to it all day. Each of those applications is one more client, and they all share the same communication channels to the controllers.

A limited, shared resource

The controllers where the control logic is configured have a finite capacity to handle communications. Every read and every write arriving from a client application takes up part of that capacity, on the same equipment that must execute process control.

Writes weigh more than reads: each one has to be received, validated and applied. An application that writes many setpoints per second, or sends them all at once, demands much more from the channel than one that only reads.

Why nobody sees it coming

  • Each client is reasonable on its own. The problem is the sum, and nobody owns the sum.
  • Applications do not know about each other. Each vendor configures its client as if it were the only one connected.
  • The load grows little by little. Variables are added, update times are shortened, a new application is installed. No single change seems important.
  • It shows up at the worst moment. During a process upset, every application reacts at the same time and writes at once.

How it shows

  1. Data reaches the applications late or with bad quality.
  2. Writes fail intermittently or take a long time to be applied.
  3. Operator displays update slowly.
  4. At the extreme, the control system's communications collapse and services must be restarted, with a direct effect on operations.

What needs to be controlled

Protecting the control system is not about disconnecting applications, but about managing what reaches it. In practice that means:

  • Limiting writes per second, so that no client can exceed what the channel supports.
  • Grouping into batches what is read and what is written, instead of sending each value separately.
  • Writing only when the value changes, rather than repeating the same setpoint on every cycle.
  • Setting update times that match the process, not the fastest ones the application allows.
  • Knowing the total load, not just the load of each client.

Doing this application by application, with each vendor, is slow and fragile: a single poorly configured client is enough to be back at the starting point.

The role of OPC Nexus

OPC Nexus sits between the plant's OPC clients and the control system. It orders writes by priority, groups them into batches and limits their rate so that the DCS server is not saturated. The control system stops serving many applications with different behaviors and receives a single, orderly and predictable flow.

Between what clients request and what reaches the control system, a write management engine combines several mechanisms:

  • Writes-per-second limit. Each channel to the control system has a configurable cap that is never exceeded. Demand above it waits its turn and is written at the permitted rate.
  • Batches. Many writes travel in a single call, which uses the server's capacity with fewer communications.
  • Priorities. Writes are served by priority level, so an operator command does not wait behind thousands of informational values.
  • Deadband. Changes smaller than a threshold defined per variable are not written, so capacity is not spent on insignificant variations.
  • Expiry. A setpoint that became obsolete while waiting, for example during a communication outage, is discarded instead of being written late.
  • Guaranteed order. The values of each variable are kept and written in sequence: a ramp arrives complete. If the server is down or saturated for a long time, the current value is kept rather than an obsolete history.
  • Circuit breaker. If the server stops responding, OPC Nexus stops insisting and retries gradually, instead of continuing to load a system that is already in trouble.

Each channel is regulated separately, so a problem in one does not affect the others.

Seeing the sum, at last

OPC Nexus also makes visible what nobody could see before. It shows the demand of each client system next to what actually goes out to the control system, what fraction of the limit is in use and who consumes the most. The difference between the two figures is the pressure the bridge is absorbing.

The result is that applications can be added to the plant without putting the stability of the control system at risk.
